บทที่ 1 บทนำ

1.1 ความเป็นมาและความสำคัญของปัญหา

ระบบใบอนุญาตทำงาน (Permit-to-Work: PTW) คือมาตรการควบคุมเชิงบริหารอย่างเป็นทางการที่สถานประกอบการอุตสาหกรรมใช้อนุญาตให้ดำเนินงานที่มิใช่งานประจำและมีความเสี่ยงสูง ภายใต้กฎหมายความปลอดภัยในการทำงานของประเทศไทย และสอดคล้องกับแนวปฏิบัติสากล งานสามประเภทได้รับการยอมรับว่ามีโอกาสก่อให้เกิดการเสียชีวิตสูงที่สุด ได้แก่ งานที่มีความร้อนและประกายไฟ งานในที่อับอากาศ และงานบนที่สูง ในสถานประกอบการกรณีศึกษา งานแต่ละประเภทถูกกำกับด้วยแบบฟอร์มกระดาษเฉพาะ คือ FM-SF-03, FM-SF-04 และ FM-SF-05 ตามลำดับ ซึ่งผู้รับเหมาต้องกรอกให้ครบถ้วน ผ่านการตรวจสอบโดยเจ้าหน้าที่ความปลอดภัยในการทำงาน (จป.) และต้องจัดเก็บไว้เพื่อการตรวจสอบตามข้อกำหนด

กระบวนการบนกระดาษที่ใช้อยู่เดิมมีการออกแบบเชิงหน้าที่ที่สมเหตุสมผล แต่มีความอ่อนแอเชิงโครงสร้างในทางปฏิบัติ ข้อบกพร่องสำคัญคือ ข้อจำกัดด้านความปลอดภัยทุกข้อถูกบังคับใช้ด้วยวิจารณญาณของมนุษย์เพียงจุดเดียวและเพียงช่วงเวลาเดียวเท่านั้น ค่าก๊าซที่คัดลอกผิด ใบรับรองที่หมดอายุไปตั้งแต่สัปดาห์ก่อน หรือถังดับเพลิงที่ระบุไว้ในรายการตรวจสอบแต่ไม่มีอยู่จริงหน้างาน ล้วนไม่สามารถถูกตรวจพบได้โดยตัวแบบฟอร์มเอง แบบฟอร์มเป็นเพียงบันทึกเชิงรับ มิได้ปฏิเสธการอนุมัติที่ไม่ปลอดภัย ดังนั้นความมั่นคงของแนวป้องกันด้านความปลอดภัยทั้งระบบจึงขึ้นอยู่กับความรอบคอบของผู้ตรวจสอบเพียงคนเดียว ซึ่งอาจต้องพิจารณาใบอนุญาตหลายสิบฉบับต่อหนึ่งกะการทำงาน

กระบวนการปัจจุบันปรากฏรูปแบบความล้มเหลวเชิงปฏิบัติการซ้ำ ๆ สี่ประการ ประการที่หนึ่ง การวัดค่าที่ไม่สามารถพิสูจน์ได้ ค่าก๊าซเชิงตัวเลขถูกเขียนด้วยลายมือโดยไม่มีหลักฐานว่าได้ใช้เครื่องมือวัดจริง ซึ่งเป็นพฤติกรรมที่เรียกว่า dry-labbing ประการที่สอง การสูญเสียการรับรู้สถานการณ์ เมื่อใบอนุญาตถูกจัดเก็บแล้ว เจ้าหน้าที่ความปลอดภัยไม่มีมุมมองรวมศูนย์ว่างานเสี่ยงสูงใดกำลังดำเนินอยู่ อยู่ที่ตำแหน่งใด หรือมีผู้ปฏิบัติงานอยู่ภายในที่อับอากาศกี่คน ณ ขณะใดขณะหนึ่ง ประการที่สาม การปิดงานที่ปราศจากการเฝ้าระวัง ใบอนุญาตงานที่มีความร้อนมักถูกลงนามปิดทันทีเมื่องานเสร็จสิ้น ทำให้การเฝ้าระวังอัคคีภัยหลังปฏิบัติงานซึ่งเป็นข้อบังคับไร้ผล ทั้งที่เหตุการณ์การติดไฟล่าช้าส่วนใหญ่เกิดขึ้นในช่วงเวลาดังกล่าว ประการที่สี่ การขาดร่องรอยการตรวจสอบ แบบฟอร์มกระดาษบันทึกเพียงลายมือชื่อ แต่มิได้บันทึกลำดับของการแก้ไข การอนุมัติ และการยกเว้นที่เกิดขึ้นก่อนหน้า ทำให้ผู้สอบสวนไม่สามารถสร้างลำดับเหตุการณ์ย้อนหลังได้เมื่อเกิดอุบัติเหตุ

ระบบจัดการใบอนุญาตทำงาน Smart Work Permit (ต่อไปนี้เรียกว่า “ระบบ”) ถูกเสนอขึ้นเพื่อตอบสนองต่อรูปแบบความล้มเหลวทั้งสี่ประการนี้โดยตรง มิใช่การแปลงกระดาษเป็นดิจิทัลเพียงเพื่อความเป็นดิจิทัล หลักการทางสถาปัตยกรรมที่นิยามระบบนี้คือ ข้อจำกัดด้านความปลอดภัยจะถูกบังคับใช้ที่ฝั่งเซิร์ฟเวอร์ ก่อนที่การอนุมัติโดยมนุษย์จะเกิดขึ้นได้ ใบอนุญาตที่มีค่าขีดจำกัดล่างของการระเบิด (Lower Explosive Limit) สูงเกินเกณฑ์ที่กำหนด จะไม่สามารถได้รับการอนุมัติจากเจ้าหน้าที่ความปลอดภัย ผู้บังคับบัญชา หรือผู้ดูแลระบบได้เลย เนื่องจากปลายทางบริการ (endpoint) สำหรับการอนุมัติจะปฏิเสธคำขอนั้นเอง ระบบจึงเปลี่ยนกฎความปลอดภัยจากคำแนะนำเชิงนโยบาย ให้กลายเป็นเงื่อนไขบังคับเชิงคำนวณที่ไม่อาจต่อรองได้

1.2 วัตถุประสงค์ของโครงการ

โครงการนี้มีวัตถุประสงค์ทั่วไปหนึ่งข้อ ซึ่งได้รับการสนับสนุนด้วยวัตถุประสงค์เฉพาะที่วัดผลได้จำนวนหกข้อ

วัตถุประสงค์ทั่วไป เพื่อออกแบบ พัฒนา และประเมินผลระบบใบอนุญาตทำงานบนเว็บ ที่ขจัดการใช้กระดาษออกจากวงจรชีวิตของใบอนุญาต และบังคับใช้ข้อจำกัดด้านความปลอดภัยในการทำงานด้วยกลไกเชิงคำนวณ แทนการอาศัยเพียงกระบวนการเชิงระเบียบปฏิบัติ

ID วัตถุประสงค์เฉพาะ เกณฑ์การตรวจสอบผล
OB-1แปลงวงจรชีวิตของใบอนุญาตให้เป็นดิจิทัลอย่างครบถ้วน ตั้งแต่การขอ การตรวจสอบความถูกต้อง การอนุมัติ การตรวจสอบหน้างาน การเฝ้าระวัง และการปิดใบอนุญาต ครอบคลุมใบอนุญาตทั้งสามประเภทไม่ต้องใช้แบบฟอร์มกระดาษเลยตลอดหนึ่งรอบวงจรใบอนุญาตในการทดสอบการยอมรับของผู้ใช้
OB-2พัฒนากลไกตรวจสอบความถูกต้องฝั่งเซิร์ฟเวอร์ ที่ระงับการอนุมัติเมื่อเกณฑ์ค่าก๊าซ ความสมบูรณ์ของใบรับรอง หรือข้อกำหนดด้านอุปกรณ์ไม่เป็นไปตามที่กำหนดกรณีทดสอบที่ป้อนค่าไม่ถูกต้องถูกปฏิเสธด้วยรหัส HTTP 400 ครบร้อยละ 100 รวมถึงคำขอที่ส่งตรงไปยัง API
OB-3จัดให้มีการตรวจสอบสถานะใบอนุญาตหน้างานด้วยรหัสคิวอาร์ รวมถึงการบันทึกเข้าและออกของผู้ปฏิบัติงานสำหรับงานในที่อับอากาศผู้ตรวจสอบเรียกดูสถานะปัจจุบันที่ถูกต้องได้ภายในเวลาไม่เกินสามวินาทีต่อการสแกนหนึ่งครั้ง
OB-4ส่งมอบแผนที่พื้นที่โรงงานแบบเรียลไทม์ ที่แสดงใบอนุญาตที่กำลังมีผลทุกฉบับเป็นหมุดสีตามระดับความเสี่ยง พร้อมจำนวนผู้ปฏิบัติงานและสถานะการนับเวลาถอยหลังแดชบอร์ดแสดงการเปลี่ยนสถานะภายในห้าวินาทีนับจากเหตุการณ์ต้นทาง
OB-5บังคับใช้ช่วงเฝ้าระวังอัคคีภัยหลังปฏิบัติงาน 30 นาที ที่ควบคุมเวลาโดยเซิร์ฟเวอร์ และสิ้นสุดด้วยภาพถ่ายที่ผ่านการตรวจสอบพิกัด GPS และเวลาประทับความพยายามปิดใบอนุญาตก่อนครบกำหนดเวลา หรือโดยไม่มีภาพถ่ายที่ถูกต้อง ถูกปฏิเสธในทุกกรณีทดสอบ
OB-6จัดเก็บบันทึกการตรวจสอบที่ไม่สามารถแก้ไขได้และเพิ่มข้อมูลได้อย่างเดียว โดยบันทึกผู้กระทำ บทบาท เวลา และความแตกต่างระดับฟิลด์ของทุกการเปลี่ยนสถานะสามารถสร้างประวัติใบอนุญาตย้อนหลังได้ครบถ้วน และไม่มีเส้นทางใดในแอปพลิเคชันที่อนุญาตให้ UPDATE หรือ DELETE บันทึกดังกล่าว

1.3 ขอบเขตของโครงการ

ขอบเขตของโครงการถูกกำหนดด้วยประเภทใบอนุญาต บทบาทผู้ใช้ ระยะการส่งมอบ และรายการสิ่งที่อยู่นอกขอบเขตอย่างชัดเจน การระบุสิ่งที่อยู่นอกขอบเขตมีความสำคัญไม่น้อยไปกว่าการระบุสิ่งที่อยู่ในขอบเขต เนื่องจากระบบความปลอดภัยที่ไม่มีขอบเขตจำกัดย่อมนำไปสู่การขยายฟังก์ชันอย่างไร้การควบคุม และทำให้การประเมินสมมติฐานหลักของโครงการขาดความชัดเจน

มิติ อยู่ในขอบเขต อยู่นอกขอบเขต
ประเภทใบอนุญาตงานที่มีความร้อนและประกายไฟ งานในที่อับอากาศ และงานบนที่สูงใบอนุญาตงานตัดแยกพลังงานไฟฟ้า (LOTO) งานขุดเจาะ งานยกเคลื่อนย้าย และงานถ่ายภาพรังสี
บทบาทผู้ใช้ผู้รับเหมา เจ้าหน้าที่ความปลอดภัย (จป.) ผู้ตรวจสอบหน้างาน และผู้ดูแลระบบบทบาทด้านการจัดซื้อ ทรัพยากรบุคคล และการจ่ายค่าจ้าง
การเก็บข้อมูลการป้อนค่าที่อ่านได้จากเครื่องมือด้วยตนเอง พร้อมภาพถ่ายหน้าจอเครื่องมือวัดซึ่งเป็นข้อบังคับการรับค่าโดยตรงจากเครื่องตรวจวัดก๊าซและเครื่องวัดความเร็วลมผ่าน Bluetooth หรือ IoT
แพลตฟอร์มProgressive Web Application สำหรับผู้ใช้หน้างาน และแดชบอร์ดเว็บแบบตอบสนองสำหรับผู้ใช้ในสำนักงานแอปพลิเคชันเนทีฟบน iOS หรือ Android ที่เผยแพร่ผ่านแอปสโตร์
การเชื่อมต่อระบบภายนอกการแจ้งเตือนผ่าน LINE, Web Push และ API พยากรณ์อากาศเฉพาะเพื่อแจ้งเตือนฝนเท่านั้นการเชื่อมต่อกับ ERP, SAP PM, CMMS หรือระบบยืนยันตัวตนขององค์กร
ภาษาส่วนติดต่อผู้ใช้ภาษาไทยเป็นหลัก พร้อมป้ายกำกับภาษาอังกฤษเป็นภาษารองภาษาอื่นนอกเหนือจากภาษาไทยและภาษาอังกฤษ
การติดตั้งใช้งานการติดตั้งแบบคอนเทนเนอร์สำหรับสถานประกอบการเดียว ภายใต้ Nginx reverse proxyการให้บริการแบบ SaaS หลายผู้เช่าสำหรับลูกค้าองค์กรหลายราย

งานถูกส่งมอบเป็นสามระยะแบบสะสม โดยแต่ละระยะให้ผลลัพธ์ที่สามารถสาธิตได้อย่างเป็นอิสระ

ระยะ ผลผลิตสำคัญ เกณฑ์ความสำเร็จ
ระยะที่ 1
รากฐานกระบวนการทำงาน		แบบฟอร์มใบอนุญาตแบบพลวัต กลไกตรวจสอบความถูกต้องฝั่งเซิร์ฟเวอร์ กระบวนการอนุมัติ การบันทึกการตรวจสอบ และการแจ้งเตือนผ่าน LINE และ Web Pushเจ้าหน้าที่ความปลอดภัยอนุมัติใบอนุญาตในรูปแบบดิจิทัลได้ พร้อมร่องรอยการตรวจสอบที่ครบถ้วน
ระยะที่ 2
รหัสคิวอาร์และการตรวจสอบหน้างาน		การออกรหัสคิวอาร์เมื่ออนุมัติ ส่วนติดต่อการสแกนบนมือถือ การบันทึกเข้าและออกของผู้ปฏิบัติงาน การจัดเก็บข้อมูลชั่วคราวขณะออฟไลน์ และการซิงโครไนซ์ภายหลังผู้ตรวจสอบสามารถตรวจสอบใบอนุญาตด้วยรหัสคิวอาร์ในพื้นที่ที่ไม่มีสัญญาณเครือข่ายได้
ระยะที่ 3
แผนที่ความปลอดภัย		แผนที่พื้นที่โรงงานแบบเรียลไทม์ หมุดสีตามระดับความเสี่ยง ตัวนับจำนวนผู้ปฏิบัติงาน และสรุปดัชนีชี้วัดสำหรับผู้บริหารเจ้าหน้าที่ความปลอดภัยเฝ้าติดตามใบอนุญาตที่มีผลทุกฉบับได้บนแดชบอร์ดเรียลไทม์เดียว

1.4 ประโยชน์ที่คาดว่าจะได้รับ

ผู้ได้รับประโยชน์ ประโยชน์ที่คาดว่าจะได้รับ ตัวชี้วัด
เจ้าหน้าที่ความปลอดภัย (จป.)ภาระการตรวจสอบเปลี่ยนจากการตรวจทานตัวเลข ไปสู่การใช้วิจารณญาณประเมินความเสี่ยงอย่างแท้จริง เนื่องจากการละเมิดเกณฑ์ถูกคัดกรองโดยระบบล่วงหน้าแล้วเวลาเฉลี่ยในการตรวจสอบต่อใบอนุญาตที่ลดลง
ผู้รับเหมายื่นคำขอจากหน้างานได้โดยไม่ต้องเดินทางไปยังสำนักงานความปลอดภัย และได้รับข้อมูลเหตุผลการปฏิเสธเป็นรายข้อทันทีระยะเวลาตั้งแต่ยื่นคำขอจนถึงผลการพิจารณาที่ลดลง
ผู้ตรวจสอบหน้างานเข้าถึงสถานะใบอนุญาตที่เชื่อถือได้ ณ จุดปฏิบัติงาน แม้ในพื้นที่ที่ไม่มีสัญญาณเครือข่ายสัดส่วนการตรวจสอบที่ยืนยันกับข้อมูลปัจจุบันของระบบ
ฝ่ายบริหารสถานประกอบการมองเห็นงานเสี่ยงสูงที่ดำเนินอยู่พร้อมกันและการกระจายตัวเชิงพื้นที่ทั่วทั้งโรงงานได้อย่างต่อเนื่องจำนวนใบอนุญาตที่มีผลซึ่งมองเห็นได้บนแดชบอร์ดเดียว
งานกำกับการปฏิบัติตามกฎหมายและการตรวจสอบสร้างประวัติของใบอนุญาตใด ๆ ย้อนหลังได้อย่างครบถ้วนและตรวจพบการแก้ไขได้ เพื่อการตรวจสอบตามกฎหมายหรือการสอบสวนอุบัติเหตุความครบถ้วนของบันทึกการตรวจสอบในใบอนุญาตที่สุ่มตรวจ
องค์กรขจัดค่าใช้จ่ายด้านการพิมพ์ การจัดเก็บเอกสาร และการค้นคืนเอกสารย้อนหลัง พร้อมลดความเสี่ยงจากการสูญหายของบันทึกจำนวนแบบฟอร์มกระดาษที่ใช้ต่อเดือน

บทที่ 2 การทบทวนวรรณกรรมและงานวิจัยที่เกี่ยวข้อง

การทบทวนนี้พิจารณาองค์ความรู้ห้ากลุ่มที่เป็นพื้นฐานของการออกแบบระบบ ได้แก่ วรรณกรรมด้านความปลอดภัยว่าด้วยความล้มเหลวของระบบใบอนุญาตทำงาน ผลิตภัณฑ์ใบอนุญาตทำงานแบบดิจิทัลที่มีอยู่ในปัจจุบัน แนวคิดทางวิศวกรรมซอฟต์แวร์ว่าด้วยตำแหน่งของการตรวจสอบความถูกต้อง สถาปัตยกรรมเว็บแอปพลิเคชันที่ทำงานได้ขณะออฟไลน์ และการเฝ้าระวังกิจกรรมอุตสาหกรรมเชิงพื้นที่ ในตอนท้ายจะระบุช่องว่างขององค์ความรู้ที่โครงการนี้มุ่งเติมเต็ม

2.1 ความล้มเหลวของมาตรการควบคุมความปลอดภัยเชิงบริหาร

วรรณกรรมด้านการสอบสวนอุบัติภัยร้ายแรงชี้ตรงกันว่า เหตุการณ์หายนะในภาคอุตสาหกรรมมิได้เกิดจากการไม่มีระบบใบอนุญาต แต่เกิดจากการเสื่อมถอยของระบบดังกล่าวในทางปฏิบัติ ข้อค้นพบที่ปรากฏซ้ำ ได้แก่ การออกใบอนุญาตโดยไม่ได้ตรวจสอบเงื่อนไขเบื้องต้นตามที่กำหนด การสันนิษฐานว่าได้ตัดแยกพลังงานและตรวจวัดบรรยากาศแล้วโดยไม่มีการยืนยัน และการส่งมอบงานระหว่างกะที่ทำให้บริบทสำคัญด้านความปลอดภัยสูญหาย แบบจำลองอุบัติเหตุเชิงองค์กรของ Reason อธิบายปรากฏการณ์นี้ว่าเป็นการเรียงตัวตรงกันของจุดอ่อนแฝงในชั้นป้องกันที่ต่อเนื่องกัน ใบอนุญาตกระดาษจึงเป็นชั้นป้องกันเพียงชั้นเดียวที่ประสิทธิผลขึ้นอยู่กับความรอบคอบของผู้กรอกทั้งหมด นัยเชิงการออกแบบที่โครงการนี้ยึดถือคือ ชั้นป้องกันที่การบังคับใช้เป็นเพียงทางเลือก ในเชิงสถิติแล้วย่อมมิใช่ชั้นป้องกันเลย

2.2 ระบบใบอนุญาตทำงานแบบดิจิทัลที่มีอยู่ในปัจจุบัน

โมดูลใบอนุญาตทำงานอิเล็กทรอนิกส์เชิงพาณิชย์มักถูกส่งมอบในฐานะส่วนประกอบหนึ่งของชุดซอฟต์แวร์ด้านสิ่งแวดล้อม อาชีวอนามัยและความปลอดภัยขนาดใหญ่ ตารางต่อไปนี้เปรียบเทียบผลิตภัณฑ์สามกลุ่มหลัก

กลุ่มผลิตภัณฑ์ ลักษณะสำคัญ ข้อจำกัดเมื่อเทียบกับโครงการนี้
ชุดซอฟต์แวร์ EHS ระดับองค์กรมีโมดูลอุบัติการณ์ การตรวจประเมิน และใบอนุญาตอย่างครบถ้วน กลไกกระบวนการทำงานปรับแต่งได้ และใช้สัญญาอนุญาตระดับองค์กรการตรวจสอบความถูกต้องมักปรับแต่งได้และผู้ใช้ที่มีสิทธิ์สูงสามารถข้ามได้ อีกทั้งค่าใช้จ่ายและภาระการตั้งค่าไม่คุ้มค่าสำหรับสถานประกอบการเดียว
เครื่องมือสร้างแบบฟอร์มดิจิทัลเก็บข้อมูลผ่านแบบฟอร์มบนมือถือแบบทั่วไป รองรับตรรกะเงื่อนไขและการแนบภาพถ่าย ติดตั้งใช้งานได้รวดเร็วกฎถูกประมวลผลที่ฝั่งไคลเอนต์ ไม่มีเครื่องสถานะเชิงโดเมน ไม่มีการนับจำนวนผู้เข้าปฏิบัติงาน และไม่มีการบังคับจับเวลาเฝ้าระวัง
ตารางคำนวณและกระบวนการเอกสารที่จัดทำขึ้นเองต้นทุนต่ำ และปรับให้เข้ากับแบบฟอร์มเฉพาะของสถานประกอบการได้ไม่มีสถานะแบบเรียลไทม์ ไม่มีร่องรอยการตรวจสอบที่แก้ไขไม่ได้ และไม่มีกลไกการตรวจสอบยืนยันหน้างาน

รูปแบบที่พบร่วมกันในทั้งสามกลุ่มคือ การแปลงเป็นดิจิทัลถูกมองว่าเป็นการปรับปรุงการจัดการเอกสารเป็นหลัก ใบอนุญาตถูกจัดเก็บได้สะดวกขึ้น แต่การตัดสินใจออกใบอนุญาตยังคงเป็นการกระทำของมนุษย์ที่ปราศจากข้อจำกัด ไม่มีกลุ่มใดที่สำรวจถือว่าค่าก๊าซที่เกินเกณฑ์เป็นเงื่อนไขบังคับเด็ดขาดที่ซอฟต์แวร์ปฏิเสธการข้ามผ่าน

2.3 ตำแหน่งของตรรกะการตรวจสอบความถูกต้อง

แนวทางการออกแบบระบบที่ปลอดภัยซึ่งเป็นที่ยอมรับ รวมถึงข้อเสนอแนะด้านการตรวจสอบข้อมูลนำเข้าของ OWASP ระบุว่า การตรวจสอบฝั่งไคลเอนต์มีไว้เพื่อความสะดวกในการใช้งาน ขณะที่การตรวจสอบฝั่งเซิร์ฟเวอร์มีไว้เพื่อความถูกต้องและความมั่นคงปลอดภัย และทั้งสองสิ่งต้องไม่ถูกนำมาปะปนกัน ในบริบทที่ความปลอดภัยเป็นเรื่องวิกฤต ข้อแตกต่างนี้ยิ่งมีน้ำหนัก เพราะไคลเอนต์มิเพียงไม่ได้รับความไว้วางใจในเชิงการโจมตีเท่านั้น แต่ยังไม่น่าเชื่อถือในเชิงข้อมูล เนื่องจากอุปกรณ์หน้างานอาจกำลังทำงานด้วยโค้ดที่แคชไว้ อาจออฟไลน์ หรืออาจถูกดัดแปลง ระบบจึงใช้บริการกฎที่มีอำนาจตัดสินเพียงชุดเดียวซึ่งติดตั้งอยู่ร่วมกับ API และนำสคีมาฝั่งไคลเอนต์ (เขียนด้วย Zod) มาใช้ซ้ำเพียงเพื่อให้ผลตอบกลับเบื้องต้นแก่ผู้ใช้เท่านั้น นิยามสคีมาชุดเดียวกันถูกใช้ร่วมกันระหว่างชั้น เพื่อประกันว่าความหมายของกฎทั้งสองฝั่งจะไม่แตกต่างกัน โดยเซิร์ฟเวอร์ยังคงเป็นผู้มีอำนาจตัดสินแต่เพียงผู้เดียว

2.4 เว็บแอปพลิเคชันแบบก้าวหน้าที่ทำงานได้ขณะออฟไลน์

โรงงานอุตสาหกรรมมักมีพื้นที่ที่ไม่มีสัญญาณวิทยุ เช่น ภายในถังบรรจุ ชั้นใต้ดิน และโครงสร้างเหล็กปิดล้อม วรรณกรรมด้านสถาปัตยกรรมแบบออฟไลน์เป็นหลักอธิบายว่า service worker ทำหน้าที่เป็นพร็อกซีเครือข่ายที่โปรแกรมได้ ซึ่งเปิดทางให้ใช้กลยุทธ์แคชก่อนแล้วจึงเรียกเครือข่าย และการซิงโครไนซ์รายการเปลี่ยนแปลงที่ค้างอยู่ในเบื้องหลัง ความยากหลักในการออกแบบคือการแก้ไขความขัดแย้งของข้อมูลเมื่อกลับมาเชื่อมต่อ โครงการนี้จำกัดปัญหาดังกล่าวโดยเจตนา กล่าวคือ อนุญาตให้สร้างเฉพาะเหตุการณ์เข้าและออกพื้นที่ขณะออฟไลน์เท่านั้น เหตุการณ์เหล่านี้เป็นแบบเพิ่มข้อมูลอย่างเดียว และแต่ละรายการมีตัวระบุที่สร้างจากฝั่งไคลเอนต์พร้อมเวลาประทับของอุปกรณ์ การกระทบยอดฝั่งเซิร์ฟเวอร์จึงลดรูปเหลือเพียงการเพิ่มข้อมูลตามลำดับแบบไม่ซ้ำซ้อน มิใช่การรวมข้อมูลทั่วไป ส่วนการอนุมัติและการปิดใบอนุญาต ซึ่งเป็นสองการตัดสินใจที่ส่งผลต่อความปลอดภัยมากที่สุด ไม่สามารถกระทำขณะออฟไลน์ได้ในทุกกรณี

2.5 การรับรู้เชิงพื้นที่และการแสดงผลสถานการณ์

แบบจำลองการรับรู้สถานการณ์สามระดับของ Endsley ได้แก่ การรับรู้องค์ประกอบ การเข้าใจความหมาย และการคาดการณ์สถานะในอนาคต เป็นรากฐานทางทฤษฎีของแดชบอร์ดแผนที่ รายการใบอนุญาตในรูปตารางรองรับได้เพียงระดับที่ 1 เท่านั้น การแสดงใบอนุญาตเป็นหมุดสีตามระดับความเสี่ยงบนผังพื้นที่โรงงาน พร้อมกำกับจำนวนผู้ปฏิบัติงานปัจจุบันและเวลาเฝ้าระวังอัคคีภัยที่เหลือ จะรองรับระดับที่ 2 และ 3 ทำให้เจ้าหน้าที่ความปลอดภัยรับรู้ถึงความใกล้ชิดที่เป็นอันตรายระหว่างงานที่มีความร้อนกับงานในที่อับอากาศที่ดำเนินอยู่พร้อมกันได้ ข้อสรุปนี้นำไปสู่การกำหนดให้แผนที่ มิใช่มุมมองรายการ เป็นหน้าจอเริ่มต้นของแดชบอร์ดเจ้าหน้าที่ความปลอดภัย

2.6 ช่องว่างขององค์ความรู้ที่ระบุได้

วรรณกรรมและผลิตภัณฑ์ที่ทบทวนมายืนยันข้อสรุปสามประการแยกจากกัน แต่ยังไม่มีการบูรณาการเข้าด้วยกัน ได้แก่ มาตรการควบคุมเชิงบริหารล้มเหลวเมื่อการบังคับใช้ขึ้นอยู่กับดุลยพินิจ การตรวจสอบที่มีอำนาจตัดสินต้องอยู่ที่ฝั่งเซิร์ฟเวอร์ และการแสดงผลเชิงพื้นที่ช่วยยกระดับการรับรู้สถานการณ์อย่างมีนัยสำคัญ ไม่มีระบบใดที่สำรวจซึ่งรวมกลไกกฎความปลอดภัยฝั่งเซิร์ฟเวอร์ที่ไม่อาจข้ามได้ การเก็บค่าการวัดที่ผูกกับหลักฐาน การตรวจสอบยืนยันหน้างานขณะออฟไลน์ และการแสดงความเสี่ยงเชิงพื้นที่แบบเรียลไทม์ ไว้ในกระบวนการใบอนุญาตทำงานเดียวกันที่ปรับให้สอดคล้องกับแบบฟอร์มตามกฎหมายไทย การผสานทั้งหมดนี้คือคุณูปการของโครงการนี้

บทที่ 3 การวิเคราะห์และออกแบบระบบ

3.1 บทนำ

บทนี้พัฒนาการออกแบบระบบจากความต้องการที่กำหนดไว้ในบทที่ 1 และจุดยืนเชิงวิเคราะห์ที่พัฒนาขึ้นในบทที่ 2 ความต้องการถูกรวบรวมด้วยสามวิธี ได้แก่ การศึกษาแบบฟอร์มทางการ FM-SF-03, FM-SF-04 และ FM-SF-05 อย่างเป็นระบบ การสัมภาษณ์ผู้แทนเจ้าหน้าที่ความปลอดภัยและผู้รับเหมาเกี่ยวกับกระบวนการปัจจุบัน และการสังเกตรูปแบบความล้มเหลวที่อธิบายไว้ในหัวข้อ 1.1 แบบจำลองที่ได้ถูกนำเสนอผ่านชิ้นงานวิเคราะห์และออกแบบมาตรฐาน ได้แก่ แผนภาพยูสเคส แผนภาพกิจกรรม แผนภาพลำดับ แผนภาพบริบท แผนภาพกระแสข้อมูล แผนภาพความสัมพันธ์ระหว่างเอนทิตี แผนภาพคลาส และการออกแบบส่วนติดต่อผู้ใช้ โดยแต่ละแผนภาพมีคำอธิบายกำกับว่าแสดงสิ่งใดและตอบสนองความต้องการข้อใด แผนภาพทั้งหมดสร้างจากแบบจำลองพื้นฐานเดียวกัน องค์ประกอบที่ปรากฏในหลายแผนภาพจึงใช้ชื่อและมีความหมายตรงกันตลอดทั้งเอกสาร

3.2 การวิเคราะห์ความต้องการของผู้ใช้

3.2.1 ความต้องการของผู้มีส่วนได้ส่วนเสีย

ผู้มีส่วนได้ส่วนเสีย ความต้องการหลัก ข้อจำกัดในการใช้งาน
ผู้รับเหมายื่นคำขอที่ครบถ้วนถูกต้องจากหน้างาน และทราบเหตุผลของการปฏิเสธได้ทันทีใช้อุปกรณ์เคลื่อนที่ สวมถุงมือ อยู่กลางแดดจัด และสัญญาณเครือข่ายไม่ต่อเนื่อง
เจ้าหน้าที่ความปลอดภัย (จป.)ประเมินความเสี่ยงคงเหลือของคำขอที่ผ่านการตรวจสอบเบื้องต้นแล้ว และเฝ้าดูงานเสี่ยงสูงที่ดำเนินอยู่พร้อมกันทั้งหมดใช้เครื่องคอมพิวเตอร์ตั้งโต๊ะหรือแท็บเล็ต เชื่อมต่อเครือข่ายตลอดเวลา และมีปริมาณใบอนุญาตต่อกะสูง
ผู้ตรวจสอบหน้างานยืนยัน ณ หน้างานว่าใบอนุญาตมีผลบังคับใช้จริง และบันทึกการเข้าออกพื้นที่ได้อย่างถูกต้องใช้อุปกรณ์เคลื่อนที่ มักไม่มีสัญญาณเครือข่าย และต้องใช้งานด้วยมือเดียว
ผู้ดูแลระบบดูแลข้อมูลผู้ใช้ บทบาท ระเบียนใบรับรอง และการปรับเทียบแผนที่พื้นที่โรงงานใช้เครื่องคอมพิวเตอร์ตั้งโต๊ะในสำนักงาน เข้าใช้งานไม่บ่อยแต่มีสิทธิ์สูง

3.2.2 ความต้องการเชิงหน้าที่

ID ความต้องการ ผู้กระทำ ลำดับความสำคัญ ระยะ
FR-01ระบบต้องแสดงแบบฟอร์มใบอนุญาตแบบพลวัต โดยฟิลด์เฉพาะประเภทเปลี่ยนตามประเภทใบอนุญาตที่เลือก ขณะที่ฟิลด์ส่วนหัวร่วมยังคงอยู่ผู้รับเหมาต้องมี1
FR-02ระบบต้องกำหนดให้แนบภาพถ่ายหน้าจอเครื่องมือวัดควบคู่กับค่าก๊าซหรือค่าความเร็วลมเชิงตัวเลขทุกค่าผู้รับเหมาต้องมี1
FR-03ระบบต้องปฏิเสธคำขออนุมัติที่ฝั่งเซิร์ฟเวอร์ สำหรับใบอนุญาตที่มีค่าออกซิเจนอยู่นอกช่วง 19.5–23.5 % หรือมีค่า LEL เกินเกณฑ์ที่ตั้งไว้ระบบต้องมี1
FR-04ระบบต้องตรวจสอบความสมบูรณ์ของใบรับรองของผู้รับผิดชอบด้านความปลอดภัยทุกตำแหน่งที่ระบุชื่อ และระงับการยื่นคำขอเมื่อมีใบรับรองใดขาดหายหรือหมดอายุระบบต้องมี1
FR-05ระบบต้องกำหนดให้ยืนยันรายการอุปกรณ์บังคับทุกข้อในรายการตรวจสอบ และต้องระบุชื่อรายการที่ยังไม่ครบเมื่อปฏิเสธคำขอระบบต้องมี1
FR-06ระบบต้องแจ้งเตือนเจ้าหน้าที่ความปลอดภัยผ่าน LINE และ Web Push ทุกครั้งที่มีการยื่นคำขอ และแจ้งผู้รับเหมาทุกครั้งที่มีผลการพิจารณาระบบต้องมี1
FR-07ระบบต้องกำหนดให้ระบุเหตุผลเป็นลายลักษณ์อักษรทุกครั้งที่ปฏิเสธ และบันทึกไว้ในบันทึกการตรวจสอบเจ้าหน้าที่ความปลอดภัย (จป.)ต้องมี1
FR-08ระบบต้องสร้างรหัสคิวอาร์ที่ไม่ซ้ำกันและผูกกับปลายทางบริการสถานะปัจจุบัน ณ ขณะที่ใบอนุญาตได้รับการอนุมัติระบบต้องมี2
FR-09เมื่อสแกนรหัสคิวอาร์ ระบบต้องแสดงแถบสถานะเต็มหน้าจอที่ใช้สีตามประเภทใบอนุญาต พร้อมแสดงค่าปัจจุบันที่เป็นตัวกำหนดสถานะผู้ตรวจสอบหน้างานต้องมี2
FR-10ระบบต้องบันทึกเหตุการณ์เข้าและออกพื้นที่ของผู้ปฏิบัติงานสำหรับใบอนุญาตงานในที่อับอากาศ และคงจำนวนคนปัจจุบันไว้ตลอดเวลาผู้ตรวจสอบหน้างานต้องมี2
FR-11ระบบต้องปฏิเสธการปิดใบอนุญาตงานในที่อับอากาศขณะที่จำนวนผู้ปฏิบัติงานภายในมากกว่าศูนย์ พร้อมระบุชื่อผู้ที่ยังอยู่ภายในระบบต้องมี2
FR-12ระบบต้องจัดคิวเหตุการณ์เข้าและออกพื้นที่ที่บันทึกขณะออฟไลน์ และซิงโครไนซ์โดยอัตโนมัติเมื่อกลับมาเชื่อมต่อผู้ตรวจสอบหน้างานต้องมี2
FR-13ระบบต้องเริ่มนับถอยหลังการเฝ้าระวังอัคคีภัย 30 นาทีที่ควบคุมโดยเซิร์ฟเวอร์เมื่อมีการแจ้งว่างานที่มีความร้อนเสร็จสิ้น และต้องระงับการปิดใบอนุญาตตลอดช่วงเวลาดังกล่าวระบบต้องมี1
FR-14ระบบต้องกำหนดให้ส่งภาพถ่ายที่มีพิกัด GPS และเวลาประทับเมื่อสิ้นสุดช่วงเฝ้าระวังอัคคีภัย และตรวจสอบพิกัดเทียบกับตำแหน่งปฏิบัติงานที่แจ้งไว้ผู้รับเหมาต้องมี1
FR-15ระบบต้องกำหนดให้มีค่าความเร็วลมที่วัดด้วยเครื่องวัดแบบพกพา ณ ระดับความสูงที่ปฏิบัติงาน โดยไม่เกิน 25 กม./ชม. สำหรับใบอนุญาตงานบนที่สูงผู้รับเหมาต้องมี1
FR-16ระบบต้องแสดงใบอนุญาตที่มีผลทุกฉบับเป็นหมุดสีบนแผนที่พื้นที่โรงงาน พร้อมจำนวนผู้ปฏิบัติงานปัจจุบันหรือเวลาเฝ้าระวังที่เหลือเจ้าหน้าที่ความปลอดภัย (จป.)ต้องมี3
FR-17ระบบต้องบันทึกรายการตรวจสอบที่แก้ไขไม่ได้สำหรับทุกการกระทำที่เปลี่ยนสถานะ โดยเก็บผู้กระทำ บทบาท เวลา และความแตกต่างระดับฟิลด์ระบบต้องมี1
FR-18ระบบต้องกำหนดให้ใบอนุญาตที่พ้นช่วงเวลามีผลโดยยังไม่ปิด หมดอายุโดยอัตโนมัติ และบันทึกการหมดอายุนั้นระบบควรมี1
FR-19ระบบต้องแจ้งเตือนสภาพฝนและเสนอให้ระงับงานชั่วคราว เมื่อบริการพยากรณ์อากาศรายงานว่ามีฝนตกในตำแหน่งของใบอนุญาตงานบนที่สูงที่กำลังมีผลระบบควรมี3
FR-20ระบบต้องแสดงรายงานสรุปสำหรับผู้บริหารเกี่ยวกับปริมาณใบอนุญาต เหตุผลการปฏิเสธ และเวลาอนุมัติเฉลี่ยเจ้าหน้าที่ความปลอดภัย (จป.)อาจมี3

3.2.3 ความต้องการที่ไม่เชิงหน้าที่

ID คุณลักษณะเชิงคุณภาพ ข้อกำหนดและเกณฑ์วัด
NFR-01ความมั่นคงของกลไกความปลอดภัยต้องไม่มีเส้นทาง API ใดที่อนุญาตให้อนุมัติหรือปิดใบอนุญาตขณะที่กฎการตรวจสอบยังไม่ผ่าน ไม่ว่าผู้เรียกใช้จะมีบทบาทใด ตรวจพิสูจน์ด้วยการทดสอบเจาะระบบ API โดยตรง
NFR-02สมรรถนะเวลาตอบสนองของ API ที่เปอร์เซ็นไทล์ที่ 95 ต่ำกว่า 500 มิลลิวินาทีสำหรับการอ่านข้อมูล และต่ำกว่า 1.5 วินาทีสำหรับการยื่นคำขอรวมขั้นตอนอัปโหลด
NFR-03ความพร้อมใช้งานความพร้อมใช้งานรายเดือนร้อยละ 99.5 ในช่วงเวลาเดินเครื่องของโรงงาน โดยใช้ API สองอินสแตนซ์กระจายโหลดภายใต้ Nginx
NFR-04ความง่ายในการใช้งานหน้างานปุ่มควบคุมหลักมีขนาดอย่างน้อย 48×48 dp เว้นระยะห่าง 16 dp ข้อความสถานะขนาดอย่างน้อย 32 sp และค่าความต่างของสีเป็นไปตาม WCAG AA โดยควรถึงระดับ AAA
NFR-05ความทนทานต่อการขัดข้องการตรวจสอบใบอนุญาตและการบันทึกการเข้าพื้นที่ต้องใช้งานได้ต่อเนื่องอย่างน้อยแปดชั่วโมงโดยไม่มีการเชื่อมต่อ และกระทบยอดข้อมูลโดยอัตโนมัติเมื่อกลับมาเชื่อมต่อ
NFR-06ความสามารถในการตรวจสอบย้อนหลังบันทึกการตรวจสอบเพิ่มข้อมูลได้อย่างเดียว บังคับใช้ด้วยความมั่นคงปลอดภัยระดับแถว และไม่มีบทบาทใดในแอปพลิเคชันที่มีสิทธิ์ UPDATE หรือ DELETE
NFR-07ความมั่นคงปลอดภัยใช้ TLS 1.2/1.3 เท่านั้น จัดการเซสชันด้วย JWT พร้อมการควบคุมเส้นทางตามบทบาท และจำกัดอัตราคำขอที่ปลายทางบริการรับคำขอ
NFR-08การรองรับภาษาท้องถิ่นป้ายกำกับที่ใช้ปฏิบัติงานทั้งหมดแสดงเป็นภาษาไทยพร้อมข้อความภาษาอังกฤษเป็นภาษารอง ให้ตรงกับถ้อยคำในแบบฟอร์มทางการ
NFR-09ความง่ายในการบำรุงรักษาเกณฑ์การตรวจสอบเป็นข้อมูลการตั้งค่า มิใช่ค่าคงที่ฝังในโปรแกรม การเปลี่ยนแปลงข้อกำหนดตามกฎหมายจึงไม่จำเป็นต้องติดตั้งตรรกะแอปพลิเคชันใหม่

3.3 แผนภาพยูสเคส (Use Case Diagram)

แผนภาพยูสเคสแสดงผู้กระทำทั้งสี่รายและขอบเขตของระบบ กรอบสี่เหลี่ยมคือขอบเขตของระบบ รูปวงรีภายในคือยูสเคส และโหนดวงกลมภายนอกคือผู้กระทำ ตัวจับเวลาของระบบถูกจำลองเป็นผู้กระทำประเภทระบบ เนื่องจากการสิ้นสุดเวลานับถอยหลังและการหมดอายุของใบอนุญาตเกิดขึ้นโดยตัวระบบเอง มิใช่โดยบุคคล

คำอธิบายแผนภาพ ลักษณะเชิงโครงสร้างที่สำคัญที่สุดคือ ยูสเคส ตรวจสอบข้อจำกัดด้านความปลอดภัย ถูกรวม (include) ไว้ทั้งในการยื่นคำขอ การอนุมัติ และการปิดใบอนุญาต จึงมิใช่ทางเลือกที่ผู้ใช้จะข้ามได้ และไม่มีเส้นเชื่อมโยงไปยังผู้กระทำที่เป็นบุคคลใด ซึ่งแสดงอย่างเป็นทางการว่าไม่มีบุคคลใดสามารถเรียกใช้หรือระงับยูสเคสนี้ได้ ยูสเคส ออกรหัสคิวอาร์ ถูกรวมไว้ในการอนุมัติ รหัสคิวอาร์จึงไม่อาจมีอยู่สำหรับใบอนุญาตที่ยังไม่ได้รับอนุมัติ ส่วนยูสเคส บันทึกการเข้าและออกพื้นที่ของผู้ปฏิบัติงาน เป็นของผู้ตรวจสอบหน้างานแต่เพียงผู้เดียว สอดคล้องกับข้อกำหนดที่ว่าจำนวนคนในพื้นที่ต้องบันทึกโดยผู้เฝ้าระวังที่ปากทางเข้า มิใช่ให้กลุ่มผู้ปฏิบัติงานแจ้งเอง

3.4 แผนภาพกิจกรรม (Activity Diagram)

แผนภาพกิจกรรมแสดงวงจรชีวิตของใบอนุญาตตั้งแต่การสร้างจนถึงการปิด โดยมีโหนดตัดสินใจ ณ ทุกข้อจำกัดที่ระบบบังคับใช้ แผนภาพครอบคลุมใบอนุญาตทั้งสามประเภท และแสดงเส้นทางของงานที่มีความร้อนไว้อย่างชัดเจนเนื่องจากเป็นประเภทเดียวที่มีสถานะเฝ้าระวังอัคคีภัย เพื่อความชัดเจนในการอ่าน วงจรชีวิตถูกนำเสนอเป็นสี่ภาพที่เชื่อมต่อกัน ได้แก่ ภาพที่ 3.4ก การยื่นคำขอจนถึงการอนุมัติ ภาพที่ 3.4ข การปฏิบัติงานจนถึงการแจ้งงานเสร็จสิ้น ภาพที่ 3.4ค ช่วงเฝ้าระวังอัคคีภัยเฉพาะงานที่มีความร้อน และภาพที่ 3.4ง การตรวจเงื่อนไขและการปิดใบอนุญาต โดยโหนด สถานะ ACTIVE และ ขอปิดใบอนุญาต เป็นจุดเชื่อมระหว่างภาพ

ภาพที่ 3.4ก — การยื่นคำขอและการอนุมัติ

ภาพที่ 3.4ข — การปฏิบัติงาน การเฝ้าระวัง และการปิดใบอนุญาต

ภาพที่ 3.4ค — ช่วงเฝ้าระวังอัคคีภัยหลังปฏิบัติงาน

ภาพที่ 3.4ง — การตรวจเงื่อนไขและการปิดใบอนุญาต

คำอธิบายแผนภาพ คุณสมบัติสามประการของแผนภาพนี้ควรได้รับการเน้นย้ำ ประการแรก การตรวจสอบความถูกต้องปรากฏสองครั้ง คือเมื่อยื่นคำขอ และอีกครั้งทันทีก่อนบันทึกการอนุมัติ เนื่องจากเงื่อนไขบางประการ เช่น การหมดอายุของใบรับรอง อาจเปลี่ยนแปลงในช่วงเวลาระหว่างสองเหตุการณ์ ประการที่สอง เส้นวนกลับจากโหนดตัดสินใจการปิดใบอนุญาตไปยังการจัดการผู้ปฏิบัติงานสะท้อนข้อกำหนด FR-11 กล่าวคือ ความพยายามปิดใบอนุญาตขณะที่ยังมีคนอยู่ภายในจะไม่ล้มเหลวอย่างเงียบ ๆ แต่จะนำผู้ใช้กลับไปสู่การตรวจนับกำลังพล ประการที่สาม เส้นทางการเฝ้าระวังอัคคีภัยไม่สามารถถูกลัดขั้นตอนได้ เนื่องจากทั้งสถานะของตัวจับเวลาและการตรวจสอบภาพถ่ายถูกประเมินที่ฝั่งเซิร์ฟเวอร์

3.5 แผนภาพลำดับ (Sequence Diagram)

แผนภาพลำดับแสดงรายละเอียดของปฏิสัมพันธ์ในการยื่นคำขอและการอนุมัติ ซึ่งเป็นการแลกเปลี่ยนที่มีความสำคัญต่อความปลอดภัยมากที่สุดในระบบ เพื่อความชัดเจนในการอ่าน ปฏิสัมพันธ์ถูกนำเสนอเป็นสองภาพ คือ ภาพที่ 3.5ก การยื่นคำขอและการตรวจสอบ และภาพที่ 3.5ข การพิจารณาอนุมัติและการแจ้งเตือน ผู้ร่วมปฏิสัมพันธ์ในแผนภาพสอดคล้องกับส่วนประกอบที่ติดตั้งใช้งานจริงตามที่ระบุไว้ในหัวข้อ 3.10

ภาพที่ 3.5ก — การยื่นคำขอและการตรวจสอบ

ภาพที่ 3.5ข — การพิจารณาอนุมัติและการแจ้งเตือน

คำอธิบายแผนภาพ กลไกตรวจสอบความถูกต้องถูกเรียกใช้โดย API เท่านั้น มิใช่โดยไคลเอนต์ การประเมินกฎจึงไม่อาจถูกข้ามได้ด้วยการดัดแปลงคำขอ คำขอที่ผู้รับเหมาส่งมาพร้อมภาพถ่ายจะถูกบันทึกหลักฐานไว้ก่อนการประเมินกฎเสมอ (ภาพที่ 3.5ก ข้อความลำดับที่ 1) คำขอที่ถูกปฏิเสธจึงยังคงมีหลักฐานไว้ตรวจสอบภายหลัง การเขียนฐานข้อมูลและการเขียนบันทึกการตรวจสอบแสดงเป็นข้อความเดียว เนื่องจากทั้งสองดำเนินการภายในทรานแซกชันเดียวกัน กล่าวคือ การเปลี่ยนสถานะใบอนุญาตและรายการตรวจสอบจะยืนยันผลหรือย้อนกลับพร้อมกันเสมอ ซึ่งเป็นไปตามข้อกำหนด NFR-06 นอกจากนี้ ขั้นตอนการอนุมัติจะประมวลผลชุดกฎทั้งหมดใหม่ (ภาพที่ 3.5ข ข้อความลำดับที่ 2) แทนที่จะเชื่อถือผลลัพธ์ที่บันทึกไว้ตั้งแต่ตอนยื่นคำขอ

3.6 แผนภาพบริบท (Context Diagram)

แผนภาพบริบท (แผนภาพกระแสข้อมูลระดับ 0) นำเสนอระบบเป็นกระบวนการเดียว และระบุเอนทิตีภายนอกทุกรายที่แลกเปลี่ยนข้อมูลกับระบบ

คำอธิบายแผนภาพ ขอบเขตของระบบถูกกำหนดด้วยเอนทิตีที่เป็นบุคคลสี่รายและบริการภายนอกสามบริการ บริการพยากรณ์อากาศส่งข้อมูลเข้าสู่ระบบเพียงทางเดียวและมีสถานะเป็นเพียงข้อมูลประกอบการพิจารณาโดยเจตนา ตามที่ระบุไว้ในหัวข้อ 2.5 และข้อกำหนด FR-15 ข้อมูลความเร็วลมที่ใช้ประกอบการอนุมัติต้องมาจากเครื่องวัดความเร็วลมหน้างาน เนื่องจากบริการพยากรณ์อากาศระดับภูมิภาครายงานสภาพ ณ ระดับพื้นดิน ซึ่งให้ค่าต่ำกว่าความเร็วลมจริงที่ระดับความสูง ไม่มีระบบภายนอกใดมีอำนาจตัดสินใจเกี่ยวกับใบอนุญาต กระแสข้อมูลขาเข้าทุกเส้นเป็นเพียงคำขอหรือข้อมูลประกอบเท่านั้น

3.7 แผนภาพกระแสข้อมูล ระดับที่ 1 (Data Flow Diagram Level 1)

การแตกกระบวนการที่ 0 ออกเป็นระดับย่อย ได้กระบวนการหกกระบวนการและแหล่งจัดเก็บข้อมูลห้าแหล่ง

ภาพที่ 3.7ก — การรับคำขอ การตรวจสอบ และการอนุมัติ

ภาพที่ 3.7ข — การตรวจสอบหน้างาน การปิดใบอนุญาต และการรายงาน

คำอธิบายแผนภาพ กระบวนการ 2.0 เป็นศูนย์กลางของแผนภาพ เนื่องจากถูกเรียกใช้จากการรับคำขอ การอนุมัติ และการปิดใบอนุญาต ซึ่งเป็นการแสดงออกในเชิงกระแสข้อมูลของหลักการเดียวกันกับที่ปรากฏเป็นยูสเคสแบบ include ในหัวข้อ 3.3 บันทึกการตรวจสอบ (D5) รับข้อมูลเขียนจากทุกกระบวนการที่เปลี่ยนสถานะ แต่ไม่ส่งกระแสข้อมูลกลับเข้าสู่กระบวนการปฏิบัติงานใด ซึ่งสะท้อนคุณลักษณะที่เพิ่มข้อมูลได้อย่างเดียวและไม่มีอำนาจตัดสิน ส่วนแฟ้มหลักฐานถูกจัดเก็บแยกจากระเบียนใบอนุญาต (D3) เนื่องจากสื่อไบนารีถูกเก็บในที่จัดเก็บอ็อบเจกต์ ขณะที่ฐานข้อมูลเชิงสัมพันธ์เก็บเพียงคีย์อ้างอิงเท่านั้น

3.8 การออกแบบฐานข้อมูล

สคีมาเชิงตรรกะถูกทำให้เป็นบรรทัดฐานถึงระดับที่สาม (Third Normal Form) ยกเว้นคอลัมน์ภาพนิ่งในบันทึกการตรวจสอบที่จงใจไม่ทำให้เป็นบรรทัดฐาน เพื่อเก็บชื่อและบทบาทของผู้กระทำ ณ เวลาที่เกิดการกระทำ ทำให้การเปลี่ยนแปลงข้อมูลบุคลากรในภายหลังไม่ส่งผลต่อระเบียนประวัติ

ภาพที่ 3.8ก — โครงสร้างใบอนุญาตและชนิดย่อย

ภาพที่ 3.8ข — ผู้ใช้ ข้อมูลประกอบใบอนุญาต และร่องรอยการตรวจสอบ

คำอธิบายแผนภาพ โครงสร้างที่ใช้เป็นแบบชนิดหลักและชนิดย่อย (supertype–subtype) โดยตาราง PERMITS เก็บฟิลด์ที่ใช้ร่วมกันในแบบฟอร์มทางการทั้งสามฉบับ ได้แก่ เลขที่อ้างอิง โครงการ ผู้รับเหมา วันที่ ช่วงเวลา หมุดตำแหน่ง หัวหน้างาน รายละเอียดงาน และสถานะ ขณะที่ตาราง PERMIT_HOTWORK, PERMIT_CONFINED และ PERMIT_HEIGHTS เก็บคุณลักษณะเฉพาะของ FM-SF-03, FM-SF-04 และ FM-SF-05 ตามลำดับ โครงสร้างนี้หลีกเลี่ยงตารางเดียวที่กว้างและมีค่าว่างจำนวนมาก ทั้งยังทำให้แต่ละชนิดย่อยพัฒนาไปตามแบบฟอร์มที่กำกับได้อย่างอิสระ ส่วนตาราง VALIDATION_RULES เป็นตารางข้อมูล มิใช่โค้ดที่ฝังไว้ ซึ่งเป็นไปตามข้อกำหนด NFR-09 กล่าวคือ การเปลี่ยนแปลงเกณฑ์ตามกฎหมายเป็นเพียงการปรับปรุงข้อมูล มิใช่การติดตั้งระบบใหม่

3.9 แผนภาพคลาส (Class Diagram)

แผนภาพคลาสแสดงแบบจำลองเชิงโดเมนฝั่งเซิร์ฟเวอร์ ซึ่งจงใจให้ใกล้เคียงกับสคีมาฐานข้อมูลแต่ไม่เหมือนกันทั้งหมด เนื่องจากพฤติกรรมถูกผูกไว้กับคลาสที่เป็นเจ้าของเงื่อนไขคงที่นั้น ๆ

ภาพที่ 3.9ก — ลำดับชั้นของคลาสใบอนุญาต

ภาพที่ 3.9ข — คลาสสนับสนุน การตรวจสอบ และการบันทึกประวัติ

คำอธิบายแผนภาพ คลาส Permit เป็นชนิดหลักเชิงนามธรรมที่ถูกทำให้เฉพาะเจาะจงด้วยใบอนุญาตทั้งสามประเภท ซึ่งสอดคล้องกับโครงสร้างตารางแบบชนิดหลักและชนิดย่อยในหัวข้อ 3.8 พฤติกรรมถูกวางไว้ ณ ตำแหน่งที่เงื่อนไขคงที่นั้นดำรงอยู่ กล่าวคือ เฉพาะ ConfinedSpacePermit เท่านั้นที่เปิดเผยเมท็อดการบันทึกเข้าและออกพื้นที่ และเฉพาะ HotWorkPermit เท่านั้นที่เปิดเผยเมท็อดการเฝ้าระวังอัคคีภัย การเรียกใช้ปฏิบัติการที่ไม่เกี่ยวข้องจึงเป็นไปไม่ได้ตั้งแต่ขั้นตอนการคอมไพล์ มิใช่ต้องอาศัยการตรวจสอบขณะทำงาน คลาส ValidationEngine มีความสัมพันธ์แบบพึ่งพา (dependency) กับ Permit มิใช่ความสัมพันธ์แบบเชื่อมโยง ซึ่งสื่อว่ากลไกนี้ประเมินใบอนุญาตโดยไม่ได้เป็นเจ้าของ และกฎของกลไกเป็นอ็อบเจกต์ที่โหลดมาจากข้อมูลการตั้งค่า ส่วนความสัมพันธ์แบบองค์ประกอบระหว่าง GasReading กับ EvidenceFile บังคับใช้ข้อกำหนดในระดับแบบจำลองว่า ค่าที่วัดได้เชิงตัวเลขไม่อาจดำรงอยู่ได้โดยปราศจากภาพถ่ายประกอบ

3.10 สถาปัตยกรรมการติดตั้งใช้งาน

เอกสารนี้ระบุโครงสร้างการทำงานขณะใช้งานจริงไว้ด้วย เนื่องจากความต้องการที่ไม่เชิงหน้าที่หลายข้อ ได้แก่ ความพร้อมใช้งาน สมรรถนะ และความสามารถในการรับไฟล์อัปโหลด ถูกตอบสนองด้วยโครงสร้างพื้นฐาน มิใช่ด้วยโค้ดของแอปพลิเคชัน

ภาพที่ 3.10ก — ชั้นผู้ใช้ พร็อกซี และชั้นบริการ

ภาพที่ 3.10ข — ชั้นข้อมูลและงานตามกำหนดเวลา

คำอธิบายแผนภาพ การใช้ API สองอินสแตนซ์ที่ไม่เก็บสถานะภายใต้ตัวกระจายโหลดแบบ least connections ให้ความซ้ำซ้อนตามที่ข้อกำหนด NFR-03 ระบุไว้ และเนื่องจากสถานะเซสชันถูกเก็บใน Redis แทนที่จะอยู่ในหน่วยความจำของโพรเซส อินสแตนซ์ใดก็สามารถให้บริการคำขอใดก็ได้ นอกจากนี้ Nginx ยังทำหน้าที่ให้บริการไฟล์ที่คอมไพล์แล้วของ Vue 3 โดยตรง และยุติการเข้ารหัส TLS ทำให้การบริหารจัดการใบรับรองรวมอยู่ที่จุดเดียว ส่วนงานตามกำหนดเวลาถูกผูกไว้กับอินสแตนซ์เดียวเพื่อป้องกันการเกิดเหตุการณ์สิ้นสุดเวลาซ้ำซ้อน

3.11 การออกแบบส่วนติดต่อผู้ใช้

การออกแบบส่วนติดต่อผู้ใช้ถูกกำกับด้วยสภาพหน้างานตามที่ระบุไว้ในข้อกำหนด NFR-04 ได้แก่ แสงแดดจัด การสวมถุงมือหนา และการตัดสินใจภายใต้แรงกดดันด้านเวลา ความประณีตเชิงสุนทรียะจึงถูกจัดลำดับความสำคัญรองจากความชัดเจนในการอ่านและการป้องกันความผิดพลาดเสมอ

3.11.1 ระบบสีตามประเภทใบอนุญาต

ระบบสีชุดเดียวถูกใช้อย่างสอดคล้องกันทั้งบนหมุดแผนที่ แถบแสดงสถานะ และป้ายกำกับในรายการ เพื่อให้ความหมายของสีที่ผู้ใช้เรียนรู้จากบริบทหนึ่งสามารถนำไปใช้กับบริบทอื่นได้ทันที

ประเภทใบอนุญาต หมุดบนแผนที่ เนื้อหาบนแถบสถานะเมื่อสแกน
งานในที่อับอากาศสีแดงเข้ม กะพริบประเภทใบอนุญาต สถานะ และจำนวนผู้ปฏิบัติงานภายในปัจจุบัน เช่น “มีผู้ปฏิบัติงานภายใน: 3 คน”
งานที่มีความร้อนและประกายไฟสีส้มเพื่อความปลอดภัยประเภทใบอนุญาต สถานะ และเวลาเฝ้าระวังอัคคีภัยที่เหลือ เช่น “เฝ้าระวังอัคคีภัย: เหลือ 15 นาที”
งานบนที่สูงสีเหลืองเตือนภัยประเภทใบอนุญาต สถานะ และความสูงที่แจ้งไว้ เช่น “กำลังปฏิบัติงานที่ความสูง 8 เมตร”

3.11.2 หน้าจอหลักของระบบ

หน้าจอ บทบาท / อุปกรณ์ เจตนาในการออกแบบ
หน้าจอเลือกประเภทใบอนุญาตผู้รับเหมา / อุปกรณ์เคลื่อนที่การ์ดเต็มความกว้างสามใบตามสีของใบอนุญาตแต่ละประเภท การเลือกที่กำหนดรูปแบบของทั้งแบบฟอร์มจึงเกิดขึ้นเพียงครั้งเดียวอย่างชัดเจน ด้วยพื้นที่กดที่ใหญ่ที่สุดในระบบ
หน้าจอแบบฟอร์มใบอนุญาตแบบพลวัตผู้รับเหมา / อุปกรณ์เคลื่อนที่การไหลของเนื้อหาแบบคอลัมน์เดียวแบ่งเป็นส่วน ๆ พร้อมตัวบอกความคืบหน้า การเปลี่ยนประเภทจะล้างเฉพาะฟิลด์เฉพาะประเภท ขณะที่ฟิลด์ส่วนหัวยังคงอยู่ ค่าที่วัดได้เชิงตัวเลขแต่ละค่าถูกจัดวางคู่กับปุ่มถ่ายภาพในกลุ่มการมองเห็นเดียวกัน
หน้าจอแสดงผลการตรวจสอบผู้รับเหมา / อุปกรณ์เคลื่อนที่ข้อที่ไม่ผ่านจากเซิร์ฟเวอร์ถูกแสดงเป็นรายการตรวจสอบทีละข้อ ระบุชื่อข้อจำกัดที่ไม่ผ่านพร้อมค่าที่กำหนด ปุ่มยื่นคำขอถูกทำให้ใช้งานไม่ได้แทนที่จะซ่อน เพื่อรักษาแบบจำลองความเข้าใจของผู้ใช้
หน้าจอคิวรอพิจารณาเจ้าหน้าที่ความปลอดภัย / คอมพิวเตอร์ตั้งโต๊ะตารางเรียงตามเวลายื่นคำขอ พร้อมป้ายประเภท ระยะเวลารอ และสถานะการตรวจสอบ เฉพาะใบอนุญาตที่ผ่านการตรวจสอบเบื้องต้นเท่านั้นที่ดำเนินการต่อได้ ทำให้ความสนใจมุ่งไปที่การใช้วิจารณญาณมากกว่าการตรวจทานตัวเลข
หน้าจอรายละเอียดการพิจารณาเจ้าหน้าที่ความปลอดภัย / คอมพิวเตอร์ตั้งโต๊ะภาพถ่ายเครื่องมือวัดถูกแสดงติดกับค่าตัวเลขที่เกี่ยวข้อง การตรวจสอบด้วยสายตาจึงไม่ต้องสลับหน้าจอ และการปฏิเสธต้องพิมพ์เหตุผลก่อนปุ่มจึงจะใช้งานได้
หน้าจอแผนที่พื้นที่โรงงานแบบเรียลไทม์เจ้าหน้าที่ความปลอดภัย / คอมพิวเตอร์ตั้งโต๊ะเป็นหน้าจอเริ่มต้น แสดงผังพื้นที่พร้อมหมุดสีตามประเภท ตัวนับแบบเรียลไทม์ และตัวกรองตามประเภทและสถานะ รองรับการเข้าใจความหมายและการคาดการณ์ มิใช่เพียงการแจกแจงรายการ
หน้าจอแถบผลการสแกนคิวอาร์ผู้ตรวจสอบหน้างาน / อุปกรณ์เคลื่อนที่แถบสีเดียวเต็มหน้าจอ ข้อความสถานะขนาด 32 sp ขึ้นไป อ่านได้ในระยะช่วงแขนกลางแสงแดด รายละเอียดรองถูกจัดวางไว้ด้านล่างของหน้าจอ
หน้าจอทะเบียนผู้เข้าปฏิบัติงานผู้ตรวจสอบหน้างาน / อุปกรณ์เคลื่อนที่แสดงจำนวนคนอย่างเด่นชัด พร้อมรายชื่อผู้ที่อยู่ภายในขณะนั้น และปุ่มบันทึกเข้าและออกขนาดใหญ่สองปุ่มที่วางแยกห่างกันเพื่อป้องกันการกดผิด
หน้าจอจับเวลาเฝ้าระวังอัคคีภัยผู้รับเหมา / อุปกรณ์เคลื่อนที่การนับถอยหลังที่ซิงโครไนซ์กับเซิร์ฟเวอร์ โดยปุ่มปิดใบอนุญาตแสดงสถานะใช้งานไม่ได้อย่างชัดเจน และปุ่มถ่ายภาพจะเปิดใช้งานเมื่อครบกำหนดเวลาเท่านั้น ทำให้กฎอธิบายตัวเองได้ในตัว
หน้าจอประวัติการตรวจสอบเจ้าหน้าที่ความปลอดภัย / คอมพิวเตอร์ตั้งโต๊ะเส้นเวลาของการกระทำเรียงตามลำดับเวลา แสดงผู้กระทำ บทบาท เวลา และความแตกต่างระดับฟิลด์ในรูปแบบคู่ค่าก่อนและหลัง

ระบบแสดงตัวบ่งชี้สถานะออฟไลน์ค้างไว้ที่ด้านบนของทุกหน้าจอบนอุปกรณ์เคลื่อนที่เมื่อไม่มีการเชื่อมต่อ พร้อมจำนวนเหตุการณ์ที่รอการซิงโครไนซ์ เพื่อให้ผู้ตรวจสอบทราบเสมอว่าสถานะที่เห็นเป็นข้อมูลปัจจุบันหรือข้อมูลที่แคชไว้

บทที่ 4 ความสามารถของระบบ

4.1 บทนำ

บทนี้อธิบายว่าระบบทำอะไรได้บ้าง โดยนำเสนอทั้งในรูปของฟังก์ชันที่ผู้ใช้มองเห็น และโมดูลที่ผู้พัฒนามองเห็น ทุกฟังก์ชันที่ระบุในบทนี้สามารถสืบย้อนไปยังความต้องการเชิงหน้าที่ในหัวข้อ 3.2.2 และยูสเคสอย่างน้อยหนึ่งรายการในหัวข้อ 3.3 และทุกโมดูลสอดคล้องกับกระบวนการอย่างน้อยหนึ่งกระบวนการในแผนภาพกระแสข้อมูลของหัวข้อ 3.7

4.2 ฟังก์ชันหลักของระบบ

ลำดับ ฟังก์ชัน คำอธิบาย สืบย้อนถึง
F1การยื่นคำขอใบอนุญาตแบบพลวัตแสดงชุดฟิลด์ที่ถูกต้องตามประเภทใบอนุญาตที่เลือก คงข้อมูลส่วนหัวที่ใช้ร่วมกันไว้เมื่อเปลี่ยนประเภท และยื่นคำขอพร้อมหลักฐานที่แนบมาFR-01, FR-02
F2การตรวจสอบความปลอดภัยที่บังคับใช้โดยเซิร์ฟเวอร์ประเมินค่าเกณฑ์ก๊าซ ความสมบูรณ์ของใบรับรอง ความครบถ้วนของอุปกรณ์ และความเร็วลม เทียบกับชุดกฎเชิงประกาศ แล้วส่งคืนรายการข้อที่ไม่ผ่านเป็นรายข้อFR-03 – FR-05, FR-15
F3กระบวนการอนุมัติและการแจ้งเตือนส่งใบอนุญาตที่ผ่านการตรวจสอบเข้าคิวของเจ้าหน้าที่ความปลอดภัย บันทึกผลการพิจารณาโดยบังคับให้ระบุเหตุผลเมื่อปฏิเสธ และแจ้งเตือนทั้งสองฝ่ายFR-06, FR-07
F4การออกรหัสคิวอาร์และการตรวจสอบหน้างานสร้างโทเคนที่ไม่ซ้ำกันเมื่ออนุมัติ และเมื่อมีการสแกนจะแปลงโทเคนเป็นแถบแสดงสถานะปัจจุบันเต็มหน้าจอที่ใช้สีตามประเภทใบอนุญาตFR-08, FR-09
F5การติดตามผู้เข้าปฏิบัติงานคงจำนวนผู้ปฏิบัติงานในที่อับอากาศให้เป็นปัจจุบันจากเหตุการณ์เข้าและออกที่สแกนได้ และเผยแพร่ไปยังแดชบอร์ดFR-10, FR-11
F6การควบคุมการเฝ้าระวังอัคคีภัยเริ่มและบังคับใช้การนับถอยหลัง 30 นาที ระงับการปิดใบอนุญาตตลอดช่วงเวลาดังกล่าว และตรวจสอบภาพถ่ายพร้อมพิกัดที่ใช้ปิดงานFR-13, FR-14
F7การทำงานขณะออฟไลน์และการซิงโครไนซ์แคชสถานะใบอนุญาตเพื่อการตรวจสอบขณะไม่มีการเชื่อมต่อ และจัดคิวเหตุการณ์เข้าและออกพื้นที่เพื่อส่งซ้ำโดยไม่เกิดรายการซ้ำซ้อนเมื่อกลับมาเชื่อมต่อFR-12
F8แผนที่ความปลอดภัยแบบเรียลไทม์แสดงใบอนุญาตที่มีผลบนผังพื้นที่โรงงานด้วยหมุดสี ตัวนับแบบเรียลไทม์ และตัวกรอง พร้อมแจ้งเตือนสภาพอากาศFR-16, FR-19
F9การตรวจสอบย้อนหลังและการรายงานบันทึกทุกการเปลี่ยนสถานะในรูปแบบที่แก้ไขไม่ได้ เปิดให้เรียกดูประวัติรายใบอนุญาต และสรุปปริมาณงาน สาเหตุการปฏิเสธ และเวลาที่ใช้อนุมัติFR-17, FR-20
F10การบริหารจัดการระบบจัดการผู้ใช้ บทบาท ระเบียนใบรับรอง เกณฑ์การตรวจสอบ และการปรับเทียบแผนที่พื้นที่โรงงาน พร้อมทำให้ใบอนุญาตที่เกินกำหนดหมดอายุโดยอัตโนมัติFR-04, FR-18, NFR-09

4.3 คำอธิบายโมดูลของระบบ

โมดูล หน้าที่ความรับผิดชอบและส่วนติดต่อหลัก กระบวนการใน DFD
M1 การยืนยันตัวตนและการให้สิทธิ์ออกและตรวจสอบเซสชัน ระบุบทบาทของผู้ใช้ และควบคุมทุกเส้นทางการเข้าถึง บทบาทถูกประเมินที่ฝั่งเซิร์ฟเวอร์ในทุกคำขอ ส่วนการควบคุมเส้นทางที่ฝั่งไคลเอนต์เป็นเพียงความสะดวกในการใช้งานเท่านั้นครอบคลุมทุกกระบวนการ
M2 การจัดการใบอนุญาตเป็นเจ้าของกลุ่มข้อมูลใบอนุญาตและเครื่องสถานะของใบอนุญาต ให้บริการปฏิบัติการสร้าง อ่าน แก้ไขฉบับร่าง ยื่นคำขอ แจ้งงานเสร็จ และปิดใบอนุญาต พร้อมปฏิเสธการเปลี่ยนสถานะใดที่ไม่อนุญาตจากสถานะปัจจุบัน1.0, 5.0
M3 กลไกตรวจสอบความถูกต้องโหลดชุดกฎตามประเภทใบอนุญาตและประเมินใบอนุญาตที่รอตรวจสอบ แล้วส่งคืนรายการข้อที่ไม่ผ่านในรูปแบบมีโครงสร้างพร้อมข้อความสองภาษา ถูกเรียกใช้ภายในระบบขณะยื่นคำขอ อนุมัติ และปิดใบอนุญาต โดยไม่เปิดเป็นปลายทางบริการสาธารณะ2.0
M4 หลักฐานและสื่อจัดการการอัปโหลดไปยังที่จัดเก็บอ็อบเจกต์ สกัดข้อมูลพิกัดภูมิศาสตร์และเวลาที่ถ่าย และเปรียบเทียบพิกัดของภาพถ่ายกับตำแหน่งปฏิบัติงานที่แจ้งไว้1.0, 5.0
M5 กระบวนการอนุมัติดูแลคิวรอพิจารณา ดำเนินการเปลี่ยนสถานะอนุมัติและปฏิเสธ บังคับให้ระบุเหตุผลเมื่อปฏิเสธ และสั่งออกรหัสคิวอาร์เมื่ออนุมัติ3.0
M6 รหัสคิวอาร์และการตรวจสอบหน้างานสร้างและแปลงโทเคนของใบอนุญาต พร้อมประกอบข้อมูลสำหรับแถบแสดงสถานะ รวมถึงค่าปัจจุบันที่เป็นตัวกำหนดสถานะของใบอนุญาตแต่ละประเภท4.0
M7 การติดตามผู้เข้าปฏิบัติงานเพิ่มเหตุการณ์เข้าและออกพื้นที่ คำนวณจำนวนคนปัจจุบัน ขจัดรายการซ้ำจากเหตุการณ์ออฟไลน์ที่ส่งซ้ำด้วยตัวระบุเหตุการณ์ฝั่งไคลเอนต์ และให้ข้อมูลเงื่อนไขเบื้องต้นสำหรับการปิดใบอนุญาต4.0, 5.0
M8 การเฝ้าระวังและการจัดตารางเวลาเริ่มตัวจับเวลาเฝ้าระวังอัคคีภัย ตรวจจับการครบกำหนดผ่านงานตามกำหนดเวลา ทำให้ใบอนุญาตที่เกินกำหนดหมดอายุ และส่งสัญญาณการเปลี่ยนสถานะที่เกิดขึ้น5.0
M9 การแจ้งเตือนส่งข้อความผ่าน LINE และ Web Push เมื่อมีการยื่นคำขอ ผลการพิจารณา การแจ้งเตือนเชิงคำแนะนำ และเหตุการณ์วิกฤต พร้อมส่งซ้ำเมื่อเกิดความล้มเหลวชั่วคราว3.0, 5.0
M10 แผนที่และการวิเคราะห์ข้อมูลรวบรวมใบอนุญาตที่มีผลและพิกัดให้เป็นหมุดบนแผนที่ ส่งข้อมูลปรับปรุงแบบเรียลไทม์ไปยังแดชบอร์ดที่เชื่อมต่ออยู่ และคำนวณตัวชี้วัดสรุป6.0
M11 การบันทึกการตรวจสอบเขียนระเบียนแบบเพิ่มข้อมูลอย่างเดียวภายในทรานแซกชันเดียวกับการเปลี่ยนสถานะ คำนวณความแตกต่างระดับฟิลด์ และให้บริการข้อมูลประวัติของใบอนุญาตครอบคลุมทุกกระบวนการ
M12 การซิงโครไนซ์ขณะออฟไลน์service worker ที่ทำงานอยู่ฝั่งไคลเอนต์ ทำหน้าที่จัดการแคช คิวเหตุการณ์ขาออก ตัวบ่งชี้สถานะการเชื่อมต่อ และการกระทบยอดข้อมูลเมื่อกลับมาเชื่อมต่อ4.0
M13 การบริหารจัดการระบบจัดการข้อมูลผู้ใช้ บริษัท ระเบียนใบรับรอง เกณฑ์การตรวจสอบ และการปรับเทียบแผนที่พื้นที่โรงงานสนับสนุน 2.0

4.4 บทบาทของผู้ใช้งาน

บทที่ 5 สรุปผลและข้อเสนอแนะ

5.1 บทนำ

บทนี้สรุปสาระสำคัญของข้อเสนอโครงการ บันทึกอุปสรรคสำคัญที่พบระหว่างการวิเคราะห์และออกแบบพร้อมแนวทางแก้ไขที่เลือกใช้ และเสนอแนะแนวทางการพัฒนาต่อยอดที่อยู่นอกขอบเขตปัจจุบัน

5.2 สรุปสาระสำคัญของโครงการ

ระบบจัดการใบอนุญาตทำงาน Smart Work Permit ทดแทนกระบวนการใบอนุญาตทำงานบนกระดาษสำหรับงานที่มีความร้อน งานในที่อับอากาศ และงานบนที่สูง ด้วยกระบวนการดิจิทัลซึ่งข้อจำกัดด้านความปลอดภัยเป็นเงื่อนไขบังคับเชิงคำนวณ มิใช่เพียงความคาดหวังเชิงระเบียบปฏิบัติ ความต้องการเชิงหน้าที่จำนวนยี่สิบข้อและความต้องการที่ไม่เชิงหน้าที่จำนวนเก้าข้อถูกกลั่นจากแบบฟอร์มทางการและจากรูปแบบความล้มเหลวที่มีการบันทึกไว้ในทางปฏิบัติปัจจุบัน และถูกจำลองผ่านแผนภาพยูสเคส แผนภาพกิจกรรม แผนภาพลำดับ แผนภาพบริบท แผนภาพกระแสข้อมูล แผนภาพความสัมพันธ์ระหว่างเอนทิตี และแผนภาพคลาส ซึ่งใช้ศัพท์เฉพาะชุดเดียวกันอย่างสอดคล้อง

คุณูปการของโครงการตั้งอยู่บนกลไกสี่ประการ ประการแรก การผูกหลักฐาน ซึ่งกำหนดให้ค่าที่วัดได้เชิงตัวเลขทุกค่าต้องมาพร้อมภาพถ่ายหน้าจอเครื่องมือวัด เพื่อแก้ปัญหาการกรอกค่าโดยไม่ได้วัดจริง ประการที่สอง การตรวจสอบที่เซิร์ฟเวอร์มีอำนาจตัดสิน ซึ่งวางการตรวจสอบค่าเกณฑ์ ใบรับรอง และอุปกรณ์ทั้งหมดไว้หลัง API ที่ไม่มีบทบาทใดข้ามได้ ประการที่สาม การพิสูจน์การมีตัวตนหน้างาน ผ่านภาพถ่ายปิดงานที่มีพิกัดภูมิศาสตร์และทะเบียนผู้เข้าปฏิบัติงานที่บันทึกด้วยการสแกนคิวอาร์ ซึ่งประกันว่าเหตุการณ์ที่บันทึกไว้สอดคล้องกับบุคคลที่อยู่หน้างานจริง และประการที่สี่ การตรวจสอบย้อนหลังที่แก้ไขไม่ได้ ซึ่งรักษาประวัติของทุกการตัดสินใจให้สร้างย้อนหลังได้ การส่งมอบแบ่งเป็นสามระยะ ได้แก่ รากฐานกระบวนการทำงาน การตรวจสอบหน้างานด้วยคิวอาร์ และแผนที่ความปลอดภัย โดยแต่ละระยะให้ผลลัพธ์ที่สาธิตได้อย่างเป็นอิสระ บนชุดเทคโนโลยี Bun และ ElysiaJS ร่วมกับ Prisma และ PostgreSQL ที่ฝั่งเซิร์ฟเวอร์ Vue 3 ร่วมกับ Vite, TailwindCSS และ PrimeVue ที่ฝั่งไคลเอนต์ และ Nginx ร่วมกับ Docker Compose ในการติดตั้งใช้งาน

5.3 ปัญหาที่พบและแนวทางแก้ไข

ปัญหา ระดับความรุนแรง การวิเคราะห์และแนวทางแก้ไขที่เลือกใช้
การกรอกค่าก๊าซที่ไม่ได้เกิดจากการตรวจวัดจริงวิกฤตฟิลด์ตัวเลขเพียงลำพังไม่มีหลักฐานยืนยันว่ามีการวัดจริง ค่าที่วัดได้ทุกค่าจึงถูกจำลองในความสัมพันธ์แบบองค์ประกอบกับ EvidenceFile โดยบังคับให้มีภาพถ่ายหน้าจอเครื่องมือวัด และเจ้าหน้าที่ผู้พิจารณาจะเปรียบเทียบภาพกับค่าที่กรอกเคียงข้างกันก่อนอนุมัติ ทั้งนี้ได้พิจารณาแนวทางรับค่าจากเครื่องมือโดยตรงแล้ว แต่ชะลอไว้เนื่องจากต้องจัดหาฮาร์ดแวร์ซึ่งอยู่นอกขอบเขตโครงการ
การหลบเลี่ยงการเฝ้าระวังอัคคีภัยด้วยการเปิดอุปกรณ์ทิ้งไว้สูงการนับถอยหลังที่ฝั่งไคลเอนต์พิสูจน์ได้เพียงว่าแอปพลิเคชันยังเปิดอยู่เท่านั้น ตัวจับเวลาจึงถูกย้ายไปที่เซิร์ฟเวอร์ และผูกกับภาพถ่ายที่มีพิกัดภูมิศาสตร์และเวลาประทับซึ่งบังคับให้ส่งเมื่อครบกำหนด โดยพิกัดจะถูกตรวจสอบเทียบกับหมุดตำแหน่งปฏิบัติงานที่แจ้งไว้ การปิดใบอนุญาตจึงต้องอาศัยการพิสูจน์การมีตัวตน มิใช่เพียงเวลาที่ผ่านไป
บริการพยากรณ์อากาศรายงานความเร็วลมที่ระดับความสูงต่ำกว่าความเป็นจริงสูงการพยากรณ์สาธารณะอธิบายสภาพระดับพื้นดินในภาพรวมของภูมิภาค และไม่สามารถแทนสภาพภูมิอากาศเฉพาะจุดบนหลังคาหรือหอสูงได้ ค่าความเร็วลมที่วัดด้วยเครื่องวัดแบบพกพา ณ ระดับความสูงที่ปฏิบัติงานจึงถูกกำหนดให้เป็นฟิลด์บังคับสำหรับการอนุมัติ ส่วนบริการพยากรณ์อากาศถูกลดบทบาทเป็นเพียงการแจ้งเตือนฝน ซึ่งเสนอให้ระงับงานได้แต่ไม่มีอำนาจอนุญาตให้ทำงาน
การพยายามปิดใบอนุญาตขณะที่ยังมีผู้ปฏิบัติงานอยู่ภายในวิกฤตคำเตือนที่ฝั่งหน้าจอสามารถกดปิดได้ ปลายทางบริการสำหรับปิดใบอนุญาตจึงถูกกำหนดให้ส่งคืนข้อผิดพลาดเมื่อจำนวนคนภายในมากกว่าศูนย์ พร้อมระบุชื่อผู้ที่ยังบันทึกเข้าอยู่ ซึ่งเปลี่ยนกล่องข้อความเชิงแนะนำให้กลายเป็นเงื่อนไขบังคับที่มีบัญชีบันทึกการเข้าออกแบบเพิ่มข้อมูลอย่างเดียวรองรับ
ไม่มีสัญญาณเครือข่ายในถังบรรจุ ชั้นใต้ดิน และพื้นที่ปิดล้อมปานกลางการอนุญาตให้แก้ไขข้อมูลได้เต็มรูปแบบขณะออฟไลน์จะก่อให้เกิดความขัดแย้งของข้อมูลที่แก้ไขได้ยากในข้อมูลที่มีผลต่อความปลอดภัย ความสามารถขณะออฟไลน์จึงถูกจำกัดไว้เพียงการตรวจสอบสถานะและการบันทึกการเข้าออกพื้นที่แบบเพิ่มข้อมูลอย่างเดียว โดยแต่ละเหตุการณ์มีตัวระบุที่สร้างจากฝั่งไคลเอนต์ ทำให้การส่งซ้ำไม่เกิดรายการซ้ำซ้อน ส่วนการอนุมัติและการปิดใบอนุญาตยังคงต้องดำเนินการขณะออนไลน์เท่านั้น
ความไม่สอดคล้องกันของกฎการตรวจสอบระหว่างไคลเอนต์กับเซิร์ฟเวอร์ปานกลางการดูแลชุดกฎสองชุดแยกจากกันย่อมทำให้ทั้งสองเบี่ยงเบนออกจากกันเมื่อเวลาผ่านไป ระบบจึงใช้นิยามสคีมา Zod ชุดเดียวร่วมกันทั้งสองชั้นสำหรับการตรวจสอบเชิงโครงสร้าง ขณะที่กฎค่าเกณฑ์ถูกเก็บเป็นข้อมูลในตาราง validation_rules และส่งให้ไคลเอนต์ ทั้งสองชั้นจึงประเมินจากแหล่งความจริงเดียวกัน โดยมีเพียงเซิร์ฟเวอร์เท่านั้นที่เป็นผู้ตัดสิน
ศัพท์สองภาษาในแบบฟอร์มตามกฎหมายปานกลางการแปลป้ายกำกับฟิลด์ภาษาไทยที่เป็นทางการมีความเสี่ยงที่จะทำให้ความสอดคล้องทางกฎหมายกับแบบฟอร์ม FM-SF-03 ถึง FM-SF-05 สูญเสียไป ระบบจึงคงถ้อยคำภาษาไทยไว้ตามต้นฉบับเป็นป้ายกำกับหลัก และใช้ภาษาอังกฤษเป็นข้อความรอง ส่วนข้อความแจ้งผลการตรวจสอบถูกจัดเก็บสองภาษาไว้ในตารางกฎ
ผู้ปฏิบัติงานยังไม่คุ้นเคยกับกระบวนการทำงานแบบดิจิทัลปานกลางความเสี่ยงด้านการยอมรับระบบถูกจัดการที่การออกแบบ มิใช่การฝึกอบรมเพียงอย่างเดียว ได้แก่ การลดจำนวนขั้นตอนให้น้อยที่สุด พื้นที่กดขนาดใหญ่พอสำหรับผู้สวมถุงมือ การใช้รหัสสีตามประเภทใบอนุญาตอย่างสอดคล้องกันในทุกหน้าจอ และการทยอยเปิดใช้งานเป็นระยะ โดยเริ่มจากรากฐานกระบวนการทำงานก่อนแล้วจึงนำการสแกนหน้างานเข้ามา

5.4 ข้อเสนอแนะสำหรับการพัฒนาต่อยอด

แนวทางการพัฒนา เหตุผลและคุณูปการที่คาดว่าจะได้รับ
การรับค่าจากเครื่องมือวัดโดยตรงเครื่องตรวจวัดก๊าซและเครื่องวัดความเร็วลมที่เชื่อมต่อผ่าน Bluetooth และส่งค่าที่วัดได้โดยตรง จะขจัดการคัดลอกค่าด้วยมือทั้งหมด และทำให้มาตรการภาพถ่ายไม่จำเป็นอีกต่อไป เป็นการปิดช่องทางการกรอกค่าโดยไม่ได้วัดจริงที่ต้นเหตุ
การเพิ่มประเภทใบอนุญาตสคีมาแบบชนิดหลักและชนิดย่อย ร่วมกับตารางกฎที่ขับเคลื่อนด้วยข้อมูล ถูกออกแบบมาเพื่อรองรับแบบฟอร์มเพิ่มเติม ใบอนุญาตงานตัดแยกพลังงานไฟฟ้า งานขุดเจาะ และงานยกเคลื่อนย้าย จึงสามารถเพิ่มเข้ามาได้โดยไม่ต้องแก้ไขเครื่องสถานะหลัก
การตรวจจับความขัดแย้งเชิงระยะใกล้เนื่องจากใบอนุญาตมีพิกัดเชิงพื้นที่กำกับอยู่ ระบบจึงสามารถแจ้งเตือนโดยอัตโนมัติเมื่อมีการอนุมัติงานที่มีความร้อนใกล้กับปากทางเข้าที่อับอากาศหรือคลังวัตถุไวไฟ ซึ่งยกระดับแดชบอร์ดจากการเฝ้าสังเกตไปสู่การคาดการณ์
การวิเคราะห์ความเสี่ยงเชิงทำนายข้อมูลบันทึกการตรวจสอบที่สะสมไว้จะทำให้สามารถระบุเชิงสถิติได้ว่าผู้รับเหมา ตำแหน่งพื้นที่ และรูปแบบกะการทำงานใดสัมพันธ์กับอัตราการปฏิเสธหรืออุบัติการณ์ที่สูงขึ้น อันนำไปสู่การแทรกแซงอย่างตรงจุด
การเชื่อมต่ออุปกรณ์สวมใส่และเครื่องตรวจวัดก๊าซการตรวจวัดบรรยากาศภายในที่อับอากาศอย่างต่อเนื่อง แทนการตรวจวัดเพียงครั้งเดียวก่อนเข้าพื้นที่ จะทำให้สามารถแจ้งเตือนให้อพยพโดยอัตโนมัติระหว่างการปฏิบัติงานได้
การเชื่อมต่อระบบยืนยันตัวตนองค์กรและระบบบำรุงรักษาการลงชื่อเข้าใช้ครั้งเดียว (Single Sign-On) และการเชื่อมโยงกับระบบบริหารงานบำรุงรักษาด้วยคอมพิวเตอร์ จะเชื่อมใบอนุญาตเข้ากับใบสั่งงาน และขจัดการป้อนข้อมูลผู้รับเหมาและสินทรัพย์ซ้ำซ้อน
การติดตั้งใช้งานหลายสถานประกอบการการขยายสคีมาด้วยมิติของสถานประกอบการและการเข้าถึงที่จำกัดตามผู้เช่า จะทำให้องค์กรกำกับดูแลได้หลายพื้นที่ ทั้งนี้ต้องทบทวนเรื่องถิ่นที่อยู่ของข้อมูลและการควบคุมการเข้าถึงประกอบด้วย
การประเมินผลเชิงประจักษ์การศึกษาเปรียบเทียบก่อนและหลังการใช้งานอย่างมีการควบคุม โดยวัดระยะเวลาการอนุมัติ สาเหตุการปฏิเสธ และการรายงานเหตุการณ์เกือบเกิดอุบัติเหตุ จะให้หลักฐานถึงผลด้านความปลอดภัยของระบบที่นอกเหนือไปจากการยอมรับเชิงหน้าที่

ภาคผนวก ก ข้อสมมติที่ระบุไว้

ข้อสมมติต่อไปนี้จำเป็นต่อการวิเคราะห์ให้สมบูรณ์ในส่วนที่เอกสารต้นทางมิได้ระบุไว้ ทุกข้อถูกแสดงไว้อย่างชัดเจนเพื่อให้สามารถยืนยันหรือแก้ไขได้ในขั้นตอนการตรวจสอบความต้องการร่วมกับสถานประกอบการ

ID ข้อสมมติ ผลกระทบหากข้อสมมติไม่เป็นจริง
A-1จำเป็นต้องมีบทบาทผู้ดูแลระบบหนึ่งบทบาท เพิ่มเติมจากบทบาทเชิงปฏิบัติการสามบทบาทที่ระบุไว้ในเอกสารข้อกำหนดต้นทางตารางสิทธิ์ตามบทบาทในหัวข้อ 4.4 ต้องได้รับการปรับแก้
A-2เอกสารข้อกำหนดต้นทางระบุเงื่อนไข LEL ไว้ที่ 0 % ในที่หนึ่ง และระบุเกณฑ์ระงับที่ 10 % ในส่วนของแบบฟอร์มงานที่มีความร้อน กฎดังกล่าวจึงถูกเก็บเป็นข้อมูลการตั้งค่าที่สถานประกอบการกำหนดเกณฑ์ได้ โดยตั้งค่าเริ่มต้นเป็นค่าที่เข้มงวดกว่าเปลี่ยนเฉพาะค่าเกณฑ์เริ่มต้นเท่านั้น ไม่ต้องแก้ไขโค้ดหรือสคีมา
A-3มีผังพื้นที่โรงงานในรูปแบบดิจิทัลพร้อมระบบพิกัดอ้างอิงที่ทราบค่า สำหรับใช้ปรับเทียบแผนที่ระยะที่ 3 ต้องเพิ่มกิจกรรมสำรวจพื้นที่เบื้องต้นก่อนจัดทำแผนที่
A-4ผู้ปฏิบัติงานแต่ละคนมีบัตรแสดงตนในรูปรหัสคิวอาร์ประจำตัว ซึ่งใช้สแกนเข้าพื้นที่อับอากาศได้ต้องเพิ่มฟังก์ชันการออกบัตรแสดงตนในโมดูล M13
A-5อุปกรณ์หน้างานเป็นสมาร์ตโฟนที่ผู้รับเหมาหรือสถานประกอบการจัดหา ซึ่งมีกล้อง GPS และเว็บเบราว์เซอร์สมัยใหม่ที่รองรับ service workerการจัดหาอุปกรณ์จะกลายเป็นเงื่อนไขพึ่งพาของโครงการ และขอบเขตการทำงานขณะออฟไลน์อาจต้องลดลง
A-6ระเบียนใบรับรองสามารถบันทึกและดูแลภายในระบบได้ โดยไม่ต้องดึงจากระบบฝึกอบรมภายนอกต้องพัฒนาส่วนเชื่อมต่อกับระบบภายนอกสำหรับการตรวจสอบความสมบูรณ์ของใบรับรอง
A-7การติดตั้งใช้งานมุ่งเป้าไปที่สถานประกอบการเดียวบนโครงสร้างพื้นฐานที่องค์กรควบคุมเอง โดยไม่มีข้อจำกัดเรื่องถิ่นที่อยู่ของข้อมูลนอกเหนือจากกฎหมายภายในประเทศโครงสร้างการติดตั้งใช้งานในหัวข้อ 3.10 ต้องได้รับการปรับแก้
A-8ความแม่นยำของ GPS บนอุปกรณ์ทั่วไปเพียงพอที่จะแยกแยะตำแหน่งปฏิบัติงานที่แจ้งไว้ออกจากตำแหน่งอื่นภายในสถานประกอบการได้ โดยใช้รัศมีความคลาดเคลื่อนที่สถานประกอบการกำหนดการตรวจสอบตำแหน่งจะมีสถานะเป็นเพียงข้อมูลประกอบ และต้องหาวิธีพิสูจน์การมีตัวตนแบบอื่นทดแทน
A-9องค์กรยอมรับการแจ้งเตือนผ่าน LINE เป็นช่องทางเชิงปฏิบัติการควบคู่กับ Web Pushโมดูล M9 ต้องเปลี่ยนไปใช้ผู้ให้บริการส่งข้อความรายอื่นแทน

ภาคผนวก ข การตรวจสอบคุณภาพและความสอดคล้องของเอกสาร

เอกสารฉบับนี้ผ่านการตรวจทานตามเกณฑ์หกประการก่อนการนำเสนอ ข้อค้นพบและการแก้ไขที่ดำเนินการถูกบันทึกไว้ดังตารางต่อไปนี้

เกณฑ์การตรวจสอบ ข้อค้นพบและการแก้ไขที่ดำเนินการ สถานะ
ความสอดคล้องของศัพท์เฉพาะเอกสารต้นทางใช้คำว่า “Safety Officer” “Supervisor” และ “จป.” สลับกัน เอกสารฉบับนี้จึงใช้คำเดียวคือ “เจ้าหน้าที่ความปลอดภัย (จป.)” ในทุกบทและทุกแผนภาพ ในทำนองเดียวกัน คำว่า “จำนวนผู้ปฏิบัติงานภายใน” ถูกใช้แทนคำที่หลากหลายเดิมในทุกข้อความเชิงข้อกำหนดแก้ไขแล้ว
ความสามารถในการสืบย้อนความต้องการความต้องการเชิงหน้าที่ทุกข้อตั้งแต่ FR-01 ถึง FR-20 ถูกทำให้เป็นจริงด้วยฟังก์ชันหลักอย่างน้อยหนึ่งฟังก์ชันในหัวข้อ 4.2 และปรากฏในแผนภาพอย่างน้อยหนึ่งแผนภาพ คอลัมน์การสืบย้อนในหัวข้อ 4.2 ถูกเพิ่มขึ้นเพื่อแสดงการจับคู่อย่างชัดเจน และได้รับการตรวจสอบความครอบคลุมครบถ้วนแล้วแก้ไขแล้ว
ความสอดคล้องระหว่างแผนภาพชื่อเอนทิตีถูกทำให้เป็นหนึ่งเดียวกันในแผนภาพกระแสข้อมูล แผนภาพความสัมพันธ์ระหว่างเอนทิตี และแผนภาพคลาส กล่าวคือ แหล่งข้อมูล “D4 บันทึกการเข้าออกพื้นที่” ตาราง entrant_logs และคลาส EntrantLog ล้วนหมายถึงแนวคิดเดียวกัน นอกจากนี้ ชุดค่าสถานะของใบอนุญาตที่ใช้ในแผนภาพกิจกรรม แผนภาพคลาส และหัวข้อ 3.8 ได้ถูกปรับให้ตรงกันเป็นชุดเดียวจำนวนแปดค่าแก้ไขแล้ว
ความขัดแย้งของข้อมูลในเอกสารต้นทางเงื่อนไข LEL ปรากฏทั้งในรูป “เท่ากับ 0 % เท่านั้น” และ “เกิน 10 % จะระงับใบอนุญาต” แทนที่จะเลือกค่าใดค่าหนึ่งโดยไม่แจ้ง เอกสารนี้จำลองกฎดังกล่าวเป็นข้อมูลการตั้งค่า และบันทึกความไม่สอดคล้องไว้เป็นข้อสมมติ ก-2 เพื่อให้สถานประกอบการยืนยันแก้ไขแล้ว
ความรัดกุมของขอบเขตความสามารถที่ถูกกล่าวถึงอย่างไม่เป็นทางการในเอกสารต้นทางแต่ไม่จำเป็นต่อวัตถุประสงค์ที่ระบุไว้ ได้แก่ การแสดงผลพื้นที่โรงงานแบบสามมิติ และการเชื่อมต่อเซนเซอร์ IoT ถูกตัดออกจากขอบเขต และย้ายไปไว้ในหัวข้อ 5.4 ในฐานะงานพัฒนาต่อยอดแก้ไขแล้ว
ความครบถ้วนของแผนภาพแผนภาพที่กำหนดไว้ครบทั้งแปดประเภทปรากฏในเอกสาร โดยบางประเภทถูกนำเสนอเป็นภาพย่อยที่เชื่อมต่อกันหลายภาพ (เช่น ภาพที่ 3.4ก–ง, 3.5ก–ข, 3.7ก–ข, 3.8ก–ข, 3.9ก–ข และ 3.10ก–ข) เพื่อให้ข้อความในแผนภาพมีขนาดที่อ่านได้ชัดเจนเมื่อพิมพ์ และแต่ละภาพมีคำอธิบายกำกับว่าแสดงสิ่งใดและตอบสนองความต้องการข้อใด ทั้งนี้ได้เพิ่มแผนภาพการติดตั้งใช้งานเข้ามาด้วย เนื่องจากความต้องการที่ไม่เชิงหน้าที่สามข้อถูกตอบสนองด้วยโครงสร้างพื้นฐาน มิใช่ด้วยตรรกะของแอปพลิเคชันแก้ไขแล้ว
